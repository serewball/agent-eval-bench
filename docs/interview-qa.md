# agent-eval-bench 面试防挖手册

> 本手册的目标：**面试官问到的每一个细节，你都能答出"是什么、为什么、怎么验证的"。**
> 使用前提：把 README 和这份手册通读两遍，把第 5 节「诚实边界」背到条件反射——**被挖穿的定义不是"答不上来"，而是"吹了没做过的事"**。

---

## 1. 三十秒项目自述（背下来）

> 我开源了一个 Agent 评测工具 agent-eval-bench，解决的是「Agent 上线前怎么证明它可靠」的问题。
> 核心是一套双口径指标：**Pass@k 衡量能力上限**（k 次采样里至少一次成功），**Pass^k 衡量业务可靠性**（k 次采样全部成功）。我用一个内置的供应链场景数据集做了演示：同一个 Agent，Pass@5 是 99.9%，但 Pass^5 只有 38.6%——意思是它每道题都做对过，但只有不到四成的任务能连续五次不出错。**查询类功能看前者就够了，改交期、取消订单这类不可逆动作只能看后者。**
> 另外做了两件事：判分器本身用人工金标 + Cohen's kappa 校准（16 条金标，κ=0.846），失败归因用规则定位到轨迹的第一个错误步骤。整个工具零依赖，`git clone` 后一条命令能跑。

关键词密度：可靠性 / 双口径 / 校准 / 归因 / 零依赖。**别说**：平台、框架、生产级。

## 2. 核心概念题（被问概率最高，按出现频率排序）

### Q1. Pass@k 是怎么算的？

**公式**：`1 - C(n-c, k) / C(n, k)`，其中 n = 每条任务的采样次数，c = 通过次数。

**直觉**：Pass@k 不是"跑 k 次然后看有没有一次过"（那样估计方差极大），而是**从已有的 n 次采样里无放回抽 k 条轨迹，抽中的全是失败轨迹的概率的补集**。`C(n-c, k) / C(n, k)` 就是"抽 k 条恰好全是失败"的概率，1 减它就是"至少一条通过"的概率。

**能倒推**：n=10、c=6、k=5 时，`1 - C(4,5)/C(10,5)`。C(4,5)=0（4 条失败里抽不出 5 条），所以等于 1.0——6 次通过里只要抽 5 条必然碰到成功的。

**追问**：为什么用组合数不用蒙特卡洛？→ 组合数是闭式解，零方差、零成本；蒙特卡洛要重复抽样才有稳定估计。

### Q2. 为什么 n 必须大于 k？（你踩过的坑）

n == k 时，`C(n-c, k) / C(n, k)` 只有当 c=0（全失败）时才非零，否则分子为 0 → Pass@k 要么 0 要么 100%，**指标饱和，任务之间失去区分度**。我第一次跑 demo 就是 `-n 5 -k 5`，结果每道题的 Pass@k 全是 100%，什么也说明不了。改成 `-n 10 -k 5` 后分布才真实。

工具里做了硬校验拒绝 n ≤ k，这是从错误里长出来的约束，不是抄文档抄来的。

### Q3. Pass^k 是什么？和 Pass@k 什么关系？

**公式**：`C(c, k) / C(n, k)` —— 从 n 次采样里随机取 k 条、**全部通过**的概率。

**对称性**：Pass@k 是"k 条里至少一条过"（上限），Pass^k 是"k 条里全部过"（下限）。n==k 时 Pass^k 退化为"n 次全中"，是最严格的可靠性口径。

**演示数据**：p=0.6 的 Agent，k=5 时 Pass@5 ≈ 99%，Pass^5 ≈ 7.8%（0.6⁵）。这一组数字就是"技术奇观 vs 业务可靠"最直观的证据。

**适用判据**：动作可逆看 Pass@k，不可逆只看 Pass^k。

### Q4. 确认合规率是怎么算的？口径为什么改过？

初版口径：轨迹里调用过 `request_confirmation` 就算合规。审计时发现这个口径有洞：**Agent 先取消订单、事后补一个确认调用，也会判通过**。安全护栏不允许这个漏洞，所以收紧为：**第一个写操作必须发生在某次 request_confirmation 之后**。现在先写后补确认的轨迹会被判失败，归因精确到「第 N 步执行 cancel_order 前未调用 request_confirmation」。

这是一个「指标定义影响行为」的例子：口径松，指标就变成了摆设。

### Q5. 为什么校准判分器用 Cohen's kappa 而不是简单一致率？

一致率的缺陷：当样本通过率本身偏离 50%（比如 80% 的答案本来就是好的），判分器**无脑全判"通过"也能拿 80% 一致率**。kappa 扣掉了"随机瞎猜也能对"的部分：

**公式**：`κ = (Po - Pe) / (1 - Pe)`，Po = 实际一致率，Pe = 随机一致率。

我的校准结果：16 条金标，一致率 93.8%，κ = 0.846，超过 0.7 的放量线。**换模型或改 rubric 必须重新校准**，κ 不达标就不让判分器进回归——这是把"判分器质量"变成了一道有数字的闸门。

**追问**：kappa 有什么局限？→ 它是二元一致性度量，对有序多档打分可以看加权 kappa；样本太小时置信区间很宽，所以 16 条只是起步，正式放量前要扩金标集。

### Q6. 失败归因为什么用规则而不是模型？

优先级：**禁止工具调用 > 参数不符 > 缺少确认 > 首个写操作 > 工具返回错误 > 未在最大步数内结束**。

三个理由：
1. **可解释**：每条归因都是"第 N 步做了什么、期望什么"，人能直接看懂；
2. **可复现**：同一条轨迹永远得到同一个结论，回归测试才能锁住它；
3. **零成本**：不用再花一次模型调用去做归因。

规则覆盖不了的模式（比如"策略对但执行绕远路"）才轮到轨迹模型——**这是排序问题，不是能力问题**。先便宜后贵，跟模型选型一个道理。

### Q7. 评估环境五要素是什么？

1. **数据集**（任务描述 + 成功判据）
2. **环境状态**（工具能操作的初始状态，每次采样深拷贝隔离）
3. **工具接口**（Agent 可用工具的定义与实现）
4. **Rubric**（怎么算过：断言 + 可选语义判分）
5. **交互协议**（Agent 的 step 接口：`reset(seed)` + `next_step(task, history)`）

五要素齐了，评估才是可移植、可复现的——换一个 Agent 只换一个要素，其余不动。

## 3. 设计决策题（证明"有判断"，不是"写了个脚本"）

### Q8. 为什么零依赖？

`git clone` 后一条命令能跑通是开源作品的第一道生死线。陌生人 10 分钟内跑不通的作品等于没写。代价是 HTTP 调用、JSON 解析都得手写（约 60 行），并且 YAML 成了可选扩展。**这是用实现成本换分发成本**，对"让别人能复现你的结论"这个目标来说是划算的。

### Q9. 为什么不用 LangSmith / DeepEval / promptfoo？

- **LangSmith**：全家桶，绑定 LangChain 生态，重量级平台，自带云服务——我要的是"小团队 30 分钟接入的轻量评测"，不是平台。
- **DeepEval / promptfoo**：都是好工具，但它们面向"模型/提示词输出质量"，我这个工具的重点是**带工具交互的 Agent 轨迹可靠性（Pass^k）+ 过程指标 + 归因**，口径不同。
- 更深一层：**这个项目本身就是一次学习实验**——把《深入理解 AI Agent》第 7 章的评估方法论工程化。复现方法论比引依赖更能证明理解。如果团队要的是快速接入，我会选 DeepEval；要的是方法论验证和教学，自研这个更合适。这个取舍我写进了 README 的设计取舍一节。

### Q10. 为什么串行不并发？

200 次 mock 运行不到 1 秒，**先测量再优化**——并发是真实模型接入、单轮耗时上秒之后的事（Roadmap 里排着）。提前写并发是用没验证过的复杂度换一个不存在的问题。

### Q11. 为什么轨迹不存数据库？

200 次运行的 JSON 足够，文件还能直接 diff、直接进 Git。上数据库是接 CI 做历史基线对比之后的事。**第一天不为想象中的第二天付账**。

### Q12. 为什么规则判分和 LLM 判分两套并行？

规则判分精确但不全面（只能查状态、调用、输出特征）；LLM 判分全面但不稳定（有自身偏见）。两套并行跑，**看它们的分歧样本**：规则过判分不过 → 回答漏了关键信息；规则不过判分过 → 判分器被"表面完整但事实错误"的回答骗了。分歧比总分更有信息量。

### Q13. 数据集为什么是虚构供应链？

两个原因：一是我有制造业背景，供应链场景是我讲得清、防得住追问的领域；二是**虚构脱敏让项目可以完全公开**——任何真实企业数据都会让开源合规成本爆炸。20 条任务刻意覆盖了查询、列表、改期、取消、升级五类意图，改期/取消任务带 `requires_confirmation`，部分任务带 `forbidden_tools`，让安全类指标也有样本。

## 4. 踩坑复盘（面试金句区，每个都是"我做的时候犯过的错"）

| # | 坑 | 现象 | 根因 | 修复 |
|---|----|------|------|------|
| 1 | **采样相关性** | Pass^k 系统性归零 | mock 随机源只按 run seed 生成，同一轮所有任务共享同一个决策，同时过或同时挂 | 随机源按 `seed|run_idx|task_id` 混合 |
| 2 | **Pass@k 饱和** | 任务级 Pass@k 全是 100% | n == k 时无偏估计退化为"至少成功一次" | 强制 n > k，默认 10/5 |
| 3 | **判分器被骗** | 判分通过率比规则高 9pt | 没有轨迹上下文时，"表面完整但实体错误"的回答能骗过判分器 | 双口径对照 + 分歧样本人工复核 + kappa 校准 |
| 4 | **消息顺序错误** | 接真实模型必报 400 | tool 消息排在了 assistant(tool_calls) 之前，违反 OpenAI 消息格式 | 调整为 assistant → tool，并加了轨迹协议单测锁死顺序 |
| 5 | **P95 退化为最大值** | n=10 时 P95 恒等于最大延迟 | 最近邻取整的分位数近似 | 改线性插值（与 numpy linear 口径一致），报告同时看均值 |

**坑 1 的追问**：你怎么发现采样相关性的？→ 观察 demo 结果时发现同一轮 20 个任务要么全过要么全挂，Pass^k 永远是 0，这和"30% 失误率"的预期完全不符，定位到随机数生成器的共享状态。

## 5. 诚实边界（红线清单，背熟）

以下事情**没做过，绝对不能说做过**；被问到就如实说"这是 Roadmap / 局限里写的"：

| 事项 | 实际情况 | 被问到的答法 |
|------|----------|--------------|
| 真实 LLM 跑评测 | ❌ 只跑过 mock 基线 | "真实模型接入接口已写好（OpenAI 兼容 + 环境变量），还没用预算跑全量；文档明确写了按预算调 n" |
| 并发 / 断点续跑 | ❌ 串行 | "Roadmap 里排着，接入真实模型前不构成瓶颈" |
| 多模型投票判分 | ❌ 没做 | "Roadmap 里排着，单模型先跑通校准闭环" |
| 真实企业数据 | ❌ 数据集全虚构 | "有意为之，虚构脱敏才能完全开源" |
| LLM 判分器 | ⚠️ 只有文本启发式占位实现 | "MockJudge 是演示校准流程的占位，真实判分必须先过 kappa 校准这道闸门" |
| 归因模型 | ⚠️ 规则启发式 | "规则优先是刻意的设计取舍，写进 README 了" |
| 生产环境使用 | ❌ 无 | "定位是评测台/实验工具，不是平台" |
| star / 用户 | 如实说 | "刚上架" |

**红线之外的加分话术**：面试官问"为什么没做 XX"，标准回答模板——「这是刻意的取舍，写在 README 设计取舍一节：……」。**主动暴露局限是防御，不是减分**。

## 7. 追问压轴题（问到就是送分题）

**Q：如果让你把这个工具做成公司内部的标准评测流程，第一步做什么？**
> 第一步不是写代码，是**定任务集的红线**：哪些动作不可逆（必须看 Pass^k）、哪些数据不能进测试集（真实客户数据）、判分器换模型后怎么重新校准。第二步把评测挂进 CI，每次 Agent 改动跑基线对比。第三步才是补并发和断点续跑。

**Q：Pass@k 高但 Pass^k 低，落地时怎么办？**
> 分场景：查询类直接上，把失败率当 SLA 监控；不可逆动作**加确认护栏**（就像我的 `requires_confirmation` 断言），把"能不能做"拆成"该不该做"——护栏把不可逆动作的风险从 Pass^k 里拆出来，剩下的交给 Pass@k 监控。

**Q：你怎么保证你的评测集本身没有数据泄漏？**
> 分两类：任务集泄漏（模型训练时见过答案）和判分器泄漏（判分器知道答案再判过程）。前者靠自建虚构数据 + 定期刷新任务集，后者靠**判分只看轨迹与输出、不给标准答案**（我的 rubric 只查事实/完整/安全三个维度，不把金标塞给判分器）。

## 8. 简历条目（最终版，可直接用）

> **agent-eval-bench（开源，Python，零依赖）**：独立设计与实现的 Agent 评测工具。核心是 Pass@k / Pass^k 双口径可靠性指标——内置供应链数据集演示了"Pass@5 = 99.9% vs Pass^5 = 38.6%"的能力与可靠性断层；支持任务集断言判分、k 次采样轨迹记录、工具错误率 / 确认合规率等过程指标与 token 成本估算；判分器经人工金标校准（Cohen's κ = 0.846）；失败归因定位到轨迹首个错误步骤。CI 覆盖 ubuntu / windows 双平台，36 个单元测试。

**面试版一句话**：
> 我做了一个开源的 Agent 评测台，核心是区分"Agent 能不能做到"（Pass@k）和"能不能每次都做到"（Pass^k），并用自己踩过的五个坑（采样相关性、指标饱和、判分器偏差等）反推了评测工具的设计约束。
